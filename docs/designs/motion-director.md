## Problem Statement

Motion graphics made with Claude (via HyperFrames) converge on the same result. Good output only happens when the user already knows how to supply style, context, and decisions up front, and most people cannot describe motion style in words. The builder wants a skill that walks the user through every style decision in order (concept, look, motion, keyframes) so the result reflects real choices. Any step can be skipped, and the agent decides that step instead.

Observed in the installed stack (read during the session):
- `/hyperframes` → `references/intent-interview.md` already runs a pitch round (5 concepts, at least 2 from the distribution tail) and asks "Storyboard?" as a run-shape question.
- `/motion-graphics`, the route for short motion pieces, is "autonomous by design — at most one clarifying question" and skips the run-shape questions. That is the exact path the builder uses most.
- Look is covered: `hyperframes-creative/frame-presets/*/frame-showcase.html` lets the user pick palette, type, and layout by eye, and writes `frame.md`.
- **Motion is not covered.** Nothing lets the user preview or lock *how things move* (easing personality, rhythm, entrance/exit grammar, transitions). The `storyboard.html` sketch pass is explicitly "no motion". This is the root of the "every Claude motion graphic moves the same" feeling: the frames differ, the motion grammar does not.

## What Makes This Cool

- **The tasting menu.** The user's own headline or logo, looping in several different motion personalities (3–4 in M1, 6 in M2) side by side. The user points at one ("that, but calmer"). A decision nobody can make in words takes seconds by eye.
- **The keyframe board.** 4–6 key poses with the easing curve and duration drawn between each pair, reviewed before the build. "Hold longer on 3", "snap into 4". The render is never a surprise unless the user wants one.
- **Motion DNA that persists.** Picks become `motion.md`, which the build is checked against. Confirmed picks become next run's recommended option when the user is choosing.

## Constraints

- **Complements HyperFrames, does not replace it.** HyperFrames builds, previews, and renders. This skill owns decisions and writes artifacts HyperFrames reads.
- **Every step is skippable except the content itself** (the text, logo, or data the piece is about). "You decide" on a step, or "you decide the rest" for all remaining steps. Users who want a one-shot surprise are first-class, not a fallback.
- **Skipping must not produce the generic result.** Agent-decided steps sample from the library with a tail constraint, the same discipline as HyperFrames' pitch round.
- **Show, don't ask.** Decisions are made on rendered previews of the user's content. Adjective questions are the fallback only.
- The builder is the first and primary user. Publishing openly comes later.

## Premises (agreed)

1. Guided, step by step, every step skippable. Skipped steps are decided by the agent through wide sampling (at least 2 non-obvious options considered), with a one-line receipt: what was picked and the obvious option passed over.
2. Show, don't ask. Each decision is made on rendered previews built from the user's content.
3. Motion is its own decision, separate from look, locked in a new `motion.md` that the build obeys.
4. The skill decides; HyperFrames builds. The skill writes `BRIEF.md`, `frame.md`, and `motion.md` (plus storyboard/board artifacts) and hands off.
5. Step order: brief → concept → look → motion → keyframes → build and render. Choices are remembered as next run's defaults.
6. Distribution: a standard skill folder in this repo. Personal use first, then public.

## Approaches Considered

### Approach A: Director skill, lean
A conversational SKILL.md running the six steps. The motion step is one throwaway HTML page with hand-written CSS/GSAP loops. It reuses frame-showcase, storyboard.html, and snapshot. Rejected as the end state because style stays in prose (it drifts), nothing enforces `motion.md`, and preview and render use different engines. **Kept as Milestone 1 of B.**

### Approach B: Director skill + motion system (CHOSEN)
Everything in A, plus a motion personality library as data, a tasting-menu generator that renders previews as a real HyperFrames project, a keyframe board with curves, a post-build obedience check against `motion.md`, and remembered taste.

### Approach C: Reference-driven
Extract motion and palette from a pasted site or video. Rejected for v1: extraction from arbitrary pages is the least reliable part and would sit in the core flow. **Deferred as a later input** that writes into the same `motion.md` format.

## Recommended Approach: B, built in two milestones

### The flow

At invocation the skill shows the step map once, then runs these steps. Cell counts and preview machinery are per milestone (see Milestones).

| # | Step | What the user sees | Skip ("you decide") behaviour | Artifact |
|---|------|--------------------|-------------------------------|----------|
| 1 | **Brief** | Asks for the content (the actual text, logo, or data), where it plays (aspect), and length | **Content is the one non-skippable input.** Skipping only defaults aspect (16:9) and length (derived from content) | brief fields (held in scratch until handoff) |
| 2 | **Concept** | 4–5 concept pitches, 3 lines each (reuses HyperFrames' pitch-round gate: ≥2 tail concepts, silhouette check) | Agent runs the gate internally and picks | `## Intent` |
| 3 | **Look** | 2–3 HyperFrames frame presets opened by eye (`frame-showcase.html`), or the user's brand spec | Agent picks a preset fitted to the concept by rotation: excludes the last 3 look picks, auto or confirmed. Receipt names the preset picked and the preset the concept most obviously suggested | `frame.md` via existing machinery |
| 4 | **Motion** | The tasting menu: personalities rendered with the user's content in the chosen look. The user picks one, or adjusts it ("A but slower") | Agent tail-samples: considers 6 (≥2 with `median_likelihood` < 0.10), excludes the last 3 motion picks, picks one, and records the most obvious one it passed over | `motion.md` |
| 5 | **Keyframes** | Keyframe board: 4–6 poses per shot with curve and duration drawn between poses | One-shot: no board, straight to build | board HTML + pose list |
| 6 | **Build and render** | Hands off to HyperFrames. `obey.mjs` runs during the workflow's verify step, then the workflow's own "preview first, or render?" gate | Render approval is never skipped. `/motion-graphics` Step 6 already asks "preview first, or render?" and renders only after an explicit answer (`motion-graphics/SKILL.md` line 22, Step 6) | composition + render |

**Premise exceptions (accepted):**
- The **Look** step previews show each preset's own sample content, not the user's. That is how `frame-showcase.html` ships. The user's content in the chosen look is first seen in the Motion step's tasting cells, which gives the user a second chance to re-open Look.
- In **M1**, tasting cells are a page the agent generates per run from a template (user's headline + `frame.md` tokens), not a HyperFrames render. So what the user picks in the preview and what the final render does can differ slightly. M2 closes this gap.

**Skip grammar.** At any step: "you decide" (this step), "you decide the rest" (all remaining steps, keyframes included; content is still required), or pick. When anything was agent-decided, the skill presents a receipts summary before handoff, with stated choices and agent choices in two groups. The user can correct any line, and a corrected summary is presented again before handoff.

**Adjusting a personality.** Adjectives map to fixed field edits defined in `motion-md-contract.md`, for example:

| Adjective | Field edit |
|---|---|
| slower / faster | multiply every `tempo.scale_ms` value by ×1.4 / ×0.7 |
| calmer | softer ease class (`expo`→`power2`) and ×1.3 stagger |
| punchier | sharper ease class and ×0.7 on the short durations |
| bouncier / stiffer | add or remove overshoot (`back`) on `enter` |

The adjusted variant is re-previewed before being locked, and recorded as `personality: custom` with `parent: <id>` and `adjustments: [...]`. Mixing two personalities ("A's easing with B's rhythm") is **not** offered in M1/M2 (see Later).

**Memory: two separate stores.**
- **Confirmed preferences:** picks the user actively made at a step, plus any agent pick the user explicitly kept when correcting the receipts summary. These only **pre-select the recommended option when the user is choosing** ("your last 3 pieces used *editorial-mask*").
- **Pick history:** every pick, auto or confirmed, with a timestamp. Used only for rotation.
- **Precedence rule:** "you decide" never applies a remembered preference. It always samples and rotates away from the last 3 entries in pick history. Remembered preferences steer active choices; "you decide" guarantees variety.

### `motion.md`: the new contract

YAML frontmatter plus a short prose rationale. Draft schema:

```yaml
personality: editorial-mask        # library id, or "custom"
parent: null                       # library id when custom
adjustments: []                    # e.g. [slower, calmer]
tempo:
  scale_ms: [150, 250, 450, 700, 1100]   # tween durations snap to this scale
easing:                            # GSAP ease names (builds are GSAP; see below)
  enter: "expo.out"
  exit:  "power2.in"
  move:  "expo.inOut"
stagger: { each_ms: 70 }           # not subject to scale snapping
holds: { min_ms: 700 }             # not subject to scale snapping; a floor
entrances: [mask-wipe, clip-reveal]    # advisory in M2
transitions: [hard-cut, mask-push]     # advisory in M2
banned: [fade-up-slide, linear-entrance, bounce]
```

**Enforcement rules (defined in `motion-md-contract.md`):**
- **Units:** milliseconds in `motion.md`. GSAP seconds are ×1000 on read.
- **Scale:** applies to tween durations only. A duration passes if it is within ±15% of some scale value. Stagger and holds are checked separately (stagger within ±15% of `each_ms`, holds ≥ `min_ms`).
- **Eases:** each tween's ease must be one of the three `easing` values, compared by GSAP ease family and direction (`expo.out` ≠ `power2.out`).
- **Runtime scope:** motion-director builds are **GSAP only** (HyperFrames' default adapter). `BRIEF.md` states this. Non-GSAP motion found by `obey.mjs` is itself reported as a violation.
- **Banned patterns** each ship with a machine-checkable signature. Examples:
  - `fade-up-slide` = one tween with opacity rising from ≤0.2 to 1, plus y moving from >0 to 0
  - `linear-entrance` = an entering tween with ease `none` or `linear`
  - `bounce` = ease family `bounce` or `elastic`

  A banned name without a signature is not allowed in the library.
- **Allowed** `entrances`/`transitions` names are **advisory** in M2. They guide the builder and are not enforced.

### Motion personality library

About 10 personalities, each a YAML file with the `motion.md` fields, a `median_likelihood` tag (drives tail sampling), and a demo snippet. Starting set: `swiss-precise`, `elastic-playful`, `cinematic-slow`, `brutalist-step`, `editorial-mask`, `liquid-morph`, `kinetic-punch`, `soft-drift`, `retro-terminal`, `luxe-minimal`. Tuning them is taste work owned by the builder. Code only makes them enforceable.

### Components

- `SKILL.md`: the step machine, skip grammar, receipts, memory rules, handoff.
- `references/`: step scripts, `motion-md-contract.md` (schema, adjective map, enforcement rules, banned signatures), handoff rules.
- `personalities/*.yaml`: the library.
- `templates/tasting.html` (M1): a page template the agent fills per run with the user's content, `frame.md` tokens, and 3–4 personality specs.
- `scripts/tasting.mjs` (M2): writes a HyperFrames tasting project (a grid of 6 cells, each looping the user's content in one personality, in the chosen look), previewed with `npx hyperframes preview`. It uses the same engine as the final render.
- `scripts/board.mjs` (M2): builds the keyframe board from the pose list, extending the `storyboard.html` cell format with curve and duration strips between poses.
- `scripts/obey.mjs` (M2): the obedience check against the enforcement rules above.

### Directory layout and HyperFrames integration

- **Scratch until handoff.** Steps 1–5 work in `.motion-director/<run-id>/` at the workspace root. That folder holds the brief fields, the tasting page or tasting project, the board, a draft `motion.md`, and the chosen `frame.md`. The final project directory does not exist yet, so nothing pollutes it.
- **At handoff:**
  1. Run `npx hyperframes init videos/<project-name> --non-interactive --example=blank --skill=<route>`. The workspace root is never initialised, following HyperFrames' own rule.
  2. Write `BRIEF.md`, `frame.md` and `motion.md` into it.
  3. Enter the route workflow. `/motion-graphics` Step 0 initialises only "when `$PROJECT_DIR/hyperframes.json` is absent", so it adopts the prepared project, and HyperFrames' state table ("`BRIEF.md` exists → execute its workflow, ask no brief questions") keeps the intent interview from re-running.
  4. The scratch folder is kept for reference and is gitignored.
- **`BRIEF.md` fields the writer must produce** (canonical frontmatter from `hyperframes/references/brief-format.md`): `workflow` (the route: `motion-graphics` for short, unnarrated pieces, otherwise HyperFrames' route-table choice), `flow: automation`, `storyboard: yes|no` (from step 5), `message`, `aspect`, `length`, plus `## Intent` (the concept), and `## Customizations`. Customizations states: "`motion.md` at the project root is binding motion doctrine; build in GSAP only; the keyframe poses in `STORYBOARD.md` are approved" (when step 5 ran).
- **Obedience check placement:** motion-director stays loaded while the route workflow runs (same agent). Its SKILL.md requires running `obey.mjs` right after the workflow's verify step and before the workflow's render question.
- **Repair loop:** at most 2 repair passes. If violations remain after that, they are listed at the render gate with a per-violation choice: fix again, or waive. Waived violations are recorded in `motion.md` as `waivers: [...]`.
- **Existing project:** if the target directory already has `hyperframes.json` or `BRIEF.md`, the skill does not initialise. It offers "revise this piece": it shows the current brief, look and motion as pre-filled answers and lets the user reopen chosen steps. Reopened steps rewrite only their artifact, and the build re-runs through the workflow. The alternative is to start a new directory.

## Success Criteria

- **M1:** the builder uses it for their next 3 real motion graphics instead of plain `/hyperframes`, and a handoff never re-triggers HyperFrames' intent interview.
- **M1:** blind test on the 3–4 tasting cells for one headline: every pair is distinguishable by eye. **M2:** the same test on 6 cells.

## Implementation status (2026-09-29)

Built in one pass: M1 and M2 together, plus fixes from two independent audits (a code-vs-docs consistency audit and a fresh-agent dry run of a 9:16 coffee-brand reel).

**Resolved open questions**
1. `hyperframes keyframes --json` reports per-tween timing and properties but **not eases**. obey.mjs therefore walks the live GSAP timeline in headless Chrome, samples real start and end values by seeking, and tells implicit default eases apart from custom function eases.
